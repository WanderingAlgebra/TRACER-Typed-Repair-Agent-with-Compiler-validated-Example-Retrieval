# 方法设计

## 任务定义

每个 benchmark 条目指定 Lean 源文件、完全限定的定理名、题型标签，以及由标记区域或唯一占位符表示的证明义务。Agent 只能替换目标局部证明区域，不允许覆盖原文件、imports 或定理头。

## 受控条件

- **A**：只提供定理陈述和局部源代码上下文。
- **B**：在 A 的基础上加入上一轮有界编译诊断。
- **C**：在 B 的基础上加入 Top-k 本地检索示例，实际示例文本逐项写入追踪记录；示例声明不得与冻结题目相同（允许 binder 改名），运行前自动检查。

三种条件保持 provider、模型、温度、最大输出长度、编译器、超时、题目顺序和修复轮数一致，只改变 prompt 上下文。项目不训练或微调模型，研究对象是编译反馈与示例检索对推理时修复过程的影响。

正式 fresh 实验为一次带唯一 `experiment_id` 的 54 任务运行。启动前归档旧日志、请求缓存、solutions、复核表和报告工件，并使用空缓存；复用缓存的运行只能用于调试或成本受限复跑，不能与严格 fresh 结果混称。

## 候选规范化

Provider 返回文本后，系统提取 JSON 中的候选字段。只有整个响应由单个 Markdown `lean`、`lean4`、`text` 或无语言代码围栏包裹时才移除围栏；不会扫描 Lean 字符串或混合说明文字中的反引号。编译边界会再次清洗候选，因此旧 SQLite 缓存中的围栏文本也遵循同一规则。规范化不改写证明逻辑，只移除明确的传输格式包装。

## 验证协议

1. 读取原始源文件但不修改它。
2. 通过配置的 provider 生成局部证明项。
3. 拒绝 `run_tac`、元编程入口和额外顶层命令；在隔离临时副本中补丁化证明，并以最小环境和临时 HOME 调用项目感知的 Lean/Lake 编译器。
4. 把原始诊断规范化为有界类别和反馈文本。
5. 最多重试三轮，编译成功或 provider 失败后立即停止。
6. 检查 54 个题目条件组合、连续轮次、单一 provider 配置、基础设施错误和缓存命中。
7. 保存成功隔离文件、失败候选和结构化追踪，生成明确标记的未复核报告草稿。
8. 由复核者逐项阅读成功证明并填写人工台账；工具只检查完整性，不自动推断或批量填充复核结论。
9. 最终导出时结构化脱敏 JSONL 中的仓库、用户和临时目录路径，拒绝疑似凭据，并生成文件校验和。请求 SQLite 不进入交接包。

远程 HTTP provider 必须使用 HTTPS，Authorization 只跟随同源重定向；成功与错误响应均有字节上限，错误只保留脱敏后的结构化摘要。最小 Lean 环境不会继承 API key、token、cookie 等父进程变量。该策略针对冻结且可信的项目源码和导入模块，不把 Lean 编译器描述为通用 OS 沙箱。

## 有效性约束

评测路径不得包含标准答案表或确定性的答案路由。正式结论必须具备真实 provider 配置、完整且无基础设施错误的 JSONL 轨迹、token/成本元数据、严格 fresh 状态，以及对每个成功证明的人工复核。18 题集合只用于验证研究流程，不构成通用自动定理证明能力的证据。
